# TP 07 : Le _Design Pattern_ Visiteur (Visitor)

[⬇️ Télécharger le TP (tp07.zip)](tp07.zip)

---

!!! note "Objectif du TP"

    L’objectif de ce TP est de comprendre et maîtriser le **design pattern comportemental : Visiteur**, en l’appliquant à une **hiérarchie d’expressions mathématiques**.

    Vous allez :

    - manipuler une structure arborescente d’expressions ;
    - ajouter de nouveaux comportements **sans modifier** les classes existantes ;
    - implémenter plusieurs visiteurs concrets (affichage, calcul) ;
    - réfléchir aux limites et aux améliorations possibles du pattern.

# Exercice 1 : Construction d’expressions

!!! note "Contexte"

    On vous fournit une hiérarchie de classes représentant des **expressions mathématiques** :

    - une classe abstraite `Expression` ;
    - plusieurs sous-classes concrètes représentant :
        - des constantes ;
        - des variables ;
        - des opérations binaires (`+`, `*`, etc.) ;
        - des fonctions mathématiques.

    Ce type de structure pourrait être utilisée dans :

    - un éditeur de documents scientifiques ;
    - un moteur de calcul symbolique ;
    - un compilateur ou interpréteur.

---

!!! question "Question 1 — Construction manuelle d’expressions"

    🔧 **Travail demandé**

    1. Construire l’expression correspondant à la formule mathématique :

        ```
        2 + x
        ```

    2. Construire ensuite l’expression correspondant à :

        ```
        (2 + x) * 5
        ```

    3. Enfin, construire l’expression correspondant à :

        ```
        cos((2 + x) * 5)
        ```

    ⚠️ **Attention**

    Pour la fonction `cos`, deux classes distinctes sont utilisées :

    - `Cos` : représente la fonction *cosinus* en tant que concept abstrait (implémente l’interface `Fonction`) ;
    - `FonctionExpression` : représente l’utilisation d’une fonction dans une expression.

    💡 *Remarque* : cette modélisation pourra être simplifiée dans une version ultérieure.

# Exercice 2 : Visiteur d’affichage

!!! note "Contexte"

    Il est actuellement impossible d’obtenir une **représentation lisible** d’une expression sans modifier les classes de la hiérarchie `Expression`.

    Nous souhaitons ajouter ce comportement **sans modifier ces classes**, en utilisant le **pattern Visiteur**.

---

!!! question "Question 2 — StringVisitor"

    🔧 **Travail demandé**

    - Implémenter une classe `StringVisitor` implémentant l’interface `Visitor`.
    - Ce visiteur devra produire une **représentation textuelle lisible** d’une expression.

    📌 **Règle importante**

    Pour **toutes les opérations**, vous devez **ajouter systématiquement des parenthèses** autour des arguments.

    **Exemples attendus** :

    ```
    (2 + x)
    ((2 + x) * 5)
    cos(((2 + x) * 5))
    ```

# Exercice 3 : Visiteur de calcul

!!! note "Contexte"

    Nous souhaitons maintenant **évaluer numériquement** une expression mathématique, en tenant compte des valeurs associées aux variables.

    Ce comportement doit être ajouté **sans modifier** les classes représentant les expressions.

---

!!! question "Question 3 — CalculVisitor"

    🔧 **Travail demandé**

    - Implémenter une classe `CalculVisitor` implémentant l’interface `Visitor`.
    - Le constructeur de `CalculVisitor` prendra en paramètre :

        ```java
        Map<String, Double> valeursVariables
        ```

    - Le visiteur devra calculer et renvoyer la valeur numérique de l’expression.

    **Exemple** :

    Pour l’expression :

    ```
    cos((2 + x) * 5)
    ```

    Et la map :

    ```
    x → 1.0
    ```

    Le résultat attendu correspond au calcul de :

    ```
    cos(15)
    ```

# Exercice 4 : Analyse critique

!!! question "Question 4 — Réflexion sur la conception"

    Après avoir réalisé ce TP, répondez de manière argumentée aux questions suivantes :

    - Le pattern Visiteur est-il réellement pertinent dans ce contexte ?
    - Quelles sont les limites de cette implémentation ?
    - Certaines opérations ne seraient-elles pas plus naturellement implémentées directement dans `Expression` ?
    - Peut-on simplifier la hiérarchie (par exemple pour la fonction `cos`) ?
    - Que se passerait-il si l’on ajoutait **un nouveau type d’expression** ?

!!! info "Compléments — Pour aller plus loin"

    De nombreux autres visiteurs pourraient être imaginés :

    - génération d’une expression **LaTeX** ;
    - transformation vers un format graphique (arbre, diagramme) ;
    - calcul **formel** de dérivées ;
    - simplification algébrique ;
    - export vers un langage cible (Java, Python, etc.).

    Ces extensions illustrent à la fois la **puissance** et les **limites** du *design pattern* Visiteur.
