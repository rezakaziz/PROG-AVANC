    TP 08 : Dependency Injection et Guice

    ⬇️ Télécharger le TP (tp08.zip)

    Objectif du TP

    L’objectif de ce TP est de comprendre et maîtriser le principe d’injection de dépendances, ainsi que son implémentation à l’aide du framework Guice.

    Vous allez :

    • identifier les limites d’une architecture basée sur des singletons ;
    • rendre explicites les dépendances entre les classes ;
    • appliquer le principe d’inversion de dépendances (DIP) ;
    • structurer une application selon une architecture en couches ;
    • écrire un code métier testable, découplé et maintenable.

    Instructions préliminaires

    Avant de commencer ce TP, vous devez :

    1. Créer un nouveau dépôt GitHub nommé tp08-dependency-injection.
    2. Ajouter le compte @rezakaziz comme collaborateur.
    3. Cloner votre dépôt et travailler de manière incrémentale : 
      git add .
git commit -m "progression"
git push
    4. Vérifier régulièrement que le projet compile et que les tests passent.

    Note

    Les tests unitaires sont à écrire par l’étudiant lorsqu’ils ne sont pas fournis.

    Contexte général

    Contexte

    Le code fourni modélise, de manière volontairement simplifiée, un système de réservation de billets de train.

    Il comprend notamment :

    • des DAO pour accéder à la base de données ;
    • une connexion JDBC ;
    • une première classe applicative (Q1) ;
    • une classe Application représentant un niveau plus métier.

    L’interface utilisateur est volontairement ignorée afin de se concentrer sur l’architecture logicielle.

    Simplifications assumées

    • Une seule connexion à la base est ouverte pour toute l’application.
    • Il n’y a pas de gestion avancée des transactions.
    • Certaines règles métier ne sont pas vérifiées (unicité des sièges, etc.).

    Exercice 1 : Rendre les dépendances explicites

    Problème

    Dans l’architecture actuelle :

    • les DAO créent eux-mêmes leurs connexions ;
    • la connexion provient indirectement d’un singleton (ConnectionFactory) ;
    • les dépendances sont cachées dans le code.

    Cette approche rend le code :

    • fortement couplé ;
    • difficile à tester ;
    • difficile à faire évoluer.

    Question 1 — Suppression des dépendances cachées

    🔧 Travail demandé

    1. Modifier la classe AbstractDAO afin que :

      • la connexion soit passée en paramètre du constructeur ;
      • aucune connexion ne soit créée de manière interne.

    2. Adapter le reste du code pour que :

      • le projet compile ;
      • les tests passent (ils peuvent être modifiés si nécessaire) ;
      • le Main fonctionne toujours.

    ⚠️ Attention

    Vous ne devez pas encore utiliser Guice dans cet exercice.

    Réflexion

    En quoi le fait de créer une dépendance (connexion) à l’intérieur d’une classe est-il contraire aux principes d’une bonne architecture logicielle ?

    Exercice 2 : Introduction de l’injection de dépendances avec Guice

    Contexte

    Actuellement, le Main instancie manuellement :

    • la connexion ;
    • les DAO ;
    • la classe Q1.

    Nous allons déléguer cette responsabilité à un framework d’injection de dépendances.

    Question 2 — Mise en place de Guice

    🔧 Travail demandé

    1. Créer un module Guice définissant les bindings nécessaires.
    2. Configurer l’injection pour créer :
      • la connexion ;
      • les DAO ;
      • la classe Q1.
    3. Modifier le Main pour :
      • créer un Injector ;
      • récupérer Q1 depuis Guice ;
      • lancer l’exécution.

    Attention

    Aucune classe métier ne doit utiliser directement new pour créer ses dépendances.

    Réflexion

    En quoi l’injection de dépendances facilite-t-elle l’écriture de tests unitaires ?

    Exercice 3 : Introduction d’une couche service

    Contexte

    La classe Q1 contient encore trop de logique applicative et manipule directement les DAO.

    Nous souhaitons introduire une couche service afin de :

    • mieux séparer les responsabilités ;
    • isoler le code métier ;
    • rendre l’application plus évolutive.

    Question 3 — ReservationService

    🔧 Travail demandé

    1. Créer une interface ReservationService.
    2. Fournir une implémentation concrète.
    3. Modifier la classe Application pour :
      • dépendre de ReservationService ;
      • ne plus accéder directement aux DAO.
    4. Adapter la configuration Guice et le Main pour construire Application au lieu de Q1.

    Note

    Application représente ici un point d’entrée métier, et non une interface utilisateur.

    Exercice 4 : Analyse critique de l’architecture

    Question 4 — Réflexion

    Après avoir réalisé ce TP, répondez de manière argumentée aux questions suivantes :

    • Quels problèmes l’injection de dépendances permet-elle de résoudre ?
    • Le framework Guice est-il indispensable ou seulement facilitateur ?
    • Quelles responsabilités doivent appartenir à la couche service ?
    • Que se passerait-il si l’on changeait de base de données ?
    • Comment cette architecture évoluerait-elle dans une application web ?

    Pour aller plus loin

    • Chargement de la configuration via un fichier .properties
    • Gestion de pools de connexions
    • Introduction de transactions
    • Comparaison avec Spring et Jakarta EE
